# Live-view checkpoint layout removal handoff

Status: **the layout-removal objective is complete, the compatibility policy has been deliberately replaced, the whole-view rebuild now refuses the restatements it can detect, the two running routes into that rebuild now restore from the view's own timeline first, no rebuild pins a base snapshot behind the rows the view's table holds, and every wait a view spends on its base table's apply says so in `live_views()`.** The layout removal landed on `puzpuzpuz_live_view` (PR #6939), and the restart route witnesses, the state-transfer family matrix, the performance matrix - instrumentation, harness, driver, result oracle and all four measurement rounds - and the format boundary itself followed it on the same branch, then a fix that stops one damaged superblock slot from blocking or resetting a view whose other slot is intact, then the rebuild restatement guard, then the in-process restore for the running doors that the guard's handoff left as the next step, then the snapshot floor that closes the guard's snapshot-behind abstention, then the `rebuild_deferred` recovery phase that reports the wait the snapshot floor introduced, then the two `base_apply_wait_*` columns that report every apply-lag wait, the ordinary drain's included. `LiveViewCheckpointAnchorRoot` and its builder are deleted, `SLOT_FORMAT_VERSION` is 2, and a checkpoint timeline declaring any other version is preserved and its view stopped, instead of the directory being deleted or its roots misread. Every route into the whole-view rebuild from the applied base now passes `LiveViewRebuildRestatementGuard`, which stops the view instead of committing a rebuild it can show would drop rows the view retains; see "Rebuild restatement guard, implemented". A base schema change or a mid-drain failure no longer reaches that rebuild unless the view cannot restore its accumulators from its own timeline in place, the way a restart does; see "Running-door restore from the timeline, implemented". And the guard no longer stands down because the rebuild's snapshot trails the view: the snapshot floor is the table's own coordinate, a running door whose view flushed past the base's apply waits for the apply through the existing apply-lag back-off, and `ABSTAIN_SNAPSHOT_BEHIND` is gone; see "Snapshot floor, implemented". That wait is now visible: while it lasts, `checkpoint_recovery_phase` reads `rebuild_deferred` with a reason naming the base table and the commit, the view stays `active`, and the phase is not a block; see "Deferred rebuild reported, implemented". And so is the same wait taken by the ordinary drain, which has no recovery to report under: `base_apply_wait_seqtxn` and `base_apply_wait_micros` name the base commit any deferred refresh waits for and how long it has waited, and the wait now ends on every path that ends it rather than only on a cycle that drained; see "The drain's apply-lag wait reported, implemented".

**The recovery half of the policy below is now withdrawn rather than pending.** The source-history preflight, the recovery bundle, the `ALTER LIVE VIEW` recovery operations, the durable recovery record and the permitted (rebuilding) upgrade are not going to be built as specified: their `coverage` requirement cannot be satisfied by any QuestDB deployment (see "Why the compatibility policy was withdrawn"). In their place a blocked view now behaves like an invalid one - it reports `invalid`, releases its base WAL floor, and the way out is the operator's `DROP` and re-CREATE. Sections describing the withdrawn machinery are kept for the record and marked `[WITHDRAWN]`; treat them as rationale, not as a work list. See "Implementation status" below for the exact split.

Source baseline: `6a2c65602856f0e3d9699c167f3c9515ae4419d1` on PR #6939. Source locations below refer to that revision; recheck them before implementing on a newer branch. It is also the comparison revision the performance matrix runs against, and a build of it plus a benchmarks-only harness patch is what produces that half of the matrix.

### Blocked-upgrade gate, implemented

This is now the whole of the compatibility policy, not a first instalment of it. `LiveViewCheckpointLifecycle.reconcile()` now classifies the directory in two steps instead of one:

- `LiveViewCheckpointSuperblock.foreignFormatVersion()` reads the format version a slot declares, from the two fields whose offsets do not move across versions: a slot declares a version only by naming it in both the version field and the magic's nibble. A version this build does not implement - in **either** direction, since an older build stamps a lower one - short-circuits everything, including the repair sweep, and reconciliation returns `isFormatBlocked()` with the version it read. Nothing on disk is opened, removed or rewritten.
- Everything else foreign - a slot in the magic family whose nibble and version field disagree, a top-level entry outside the layout, a catalogue that has lost track of its own files - keeps the old `isFormatReset()` disposition. Those carry no declared format to preserve the directory for, and derived state that cannot be read is cheaper to rebuild than to keep. The one exception is a damaged slot beside a slot this build selects, which is neither blocked nor reset; see "Single-slot format damage, implemented" below. A magic outside the family - zeroed, unwritten, short, unrelated - is classified by neither probe and left to A/B selection.

The caller side of that disposition:

- `CairoEngine`'s catalogue load marks the instance `LiveViewCheckpointRecoveryPhase.BLOCKED` with an operator reason naming both versions. It publishes no head checkpoint and adopts no generation, because it read none.
- `LiveViewRefreshJob.refreshInstance()` declines the whole turn ahead of every other guard - restore, seed sweep, drain, flush and seal alike - so no watermark advances and no generic missing-timeline recovery reaches the directory. It records the `upgrade_blocked` route from the turn that declined.
- `LiveViewCheckpointTimelineStoreWriter.append()` refuses to publish over a blocked directory (`CairoException.LV_CHECKPOINT_FORMAT_BLOCKED`), covering a directory that turned foreign under a running view.
- `WalPurgeJob` releases a blocked view's base WAL floor, in the same arm that releases a dropped or invalid view's. A blocked view's own watermark never advances, so any floor it publishes is frozen, and a frozen floor grows the base table's WAL without bound - on a base every other writer and view shares. This replaces the whole-WAL hold the first cut took; see "A blocked view is a stopped view" below for what it costs and why it is still right.
- `live_views()` publishes `checkpoint_recovery_phase` and `checkpoint_recovery_reason`, reports `view_status` as `invalid`, and mirrors the recovery reason through `invalidation_reason`.

The phase is derived, not persisted: every restart re-reads the superblock and reaches the same disposition, so a blocked view survives restarts with no marker file of its own, and a build that does implement the version simply never reaches the block. There is no unblock operation, by design - the way back is a build that reads the format, or the operator's re-CREATE.

`LiveViewCheckpointForwardCompatTest.testAFutureSuperblockFormatVersionBlocksTheViewAndKeepsWhatItHas` is the acceptance case: it stamps a future version over a sealed five-boundary ladder, restarts, and asserts the file inventory is unchanged to the file, the rows are still served, a base commit made while blocked moves neither the rows nor the watermark, `live_views()` reports `invalid` with the phase and a mirrored reason, a second restart reaches the same disposition, and then - after stamping this build's own version back - that the view resumes off the preserved roots (`timeline_restore`, not a rebuild) and materializes the commit that arrived while it was blocked. `testABlockedViewReleasesItsBaseWalFloor` is the companion case for the floor and its price.

### A blocked view is a stopped view

The policy question the rest of this document was built around - *may the database rebuild this view from source without silently changing its results?* - is now answered by not asking it. The database stops, says why, and leaves the decision to the operator.

A blocked view therefore carries an invalid view's operational properties, because those are the ones an indefinitely stopped view needs. The same properties, and the same price, now also belong to a view whose rebuild from the applied base was refused - phase `rebuild_blocked` rather than `blocked`; see "Rebuild restatement guard, implemented":

- **It reports as stopped.** `live_views().view_status` reads `invalid` and `invalidation_reason` mirrors the recovery reason, so the queries operators already run to find stopped views find it. `checkpoint_recovery_phase` is what tells a format block apart from a durable invalidation.
- **It releases its base WAL floor.** This is the correction that made the rest of the policy viable. A blocked view's watermark never advances, so any floor it holds is frozen, and a frozen floor grows the base table's WAL without bound - on a base every other writer and view shares. A state that pins WAL cannot be a resting state, and blocking has to be one now that nothing automatic clears it.
- **It is not a durable invalidation.** `_lv.s.invalid` stays clear and the phase is re-derived from the superblock on every start, so a build that does implement the format resumes the view with no operator action. That is what makes an accidental downgrade recoverable by going back rather than by re-creating anything.
- **The exit is the operator's.** `SHOW CREATE LIVE VIEW`, then `DROP LIVE VIEW` and re-CREATE. No new SQL, and exactly the right semantics: a deliberate recreation from currently retained data, with explicitly different historical results, which is what this document already called it.

**What the released floor costs, stated rather than hidden.** A restore replays the base WAL between its head checkpoint's boundary and the applied watermark. A view whose block outlives a purge sweep no longer has that WAL, so a later readable build cannot resume off the roots the block preserved: it spends the flush-retry budget on the missing segment and lands in `rederiveFromAppliedBaseAfterWalLoss`, recomputing the view from whatever source rows survive today - the outcome the block exists to avoid. Blocking buys time to go back to a build that reads the format; it is not a state to rest in, and the doc-visible exit is what the operator should reach for instead. `LiveViewCheckpointForwardCompatTest.testABlockedViewReleasesItsBaseWalFloor` pins both halves: the floor is released, and the resume takes the WAL-loss re-derive with the log line that names it.

While writing that case, the first cut's WAL assertion turned out to have been vacuous: `WalPurgeJob.runSerially()` is interval-gated off the millisecond clock, which the suite freezes, so `purgeJob.drain(0)` swept nothing and `countWalSegments(...) >= before` passed without a purge ever running. The new case sets `cairo.wal.purge.interval` to 0, advances the frozen clock, and sets one WAL segment per commit, and only then does the count move.

### The format boundary, implemented

`LiveViewCheckpointAnchorRoot` and `LiveViewCheckpointAnchorRootBuilder` are deleted, and `SLOT_FORMAT_VERSION` moved 1 -> 2 with them. The two had to land together: deleting the decoder is what makes the bump *necessary* - without it a 10.0.x directory reads as native, reaches a reader that no longer knows the shape, and its `window state root page kind unknown` is classified as recoverable corruption, which rebuilds the view from whatever source rows survive today, silently. The bump is what makes the deletion *safe* - it turns that ending into the block, which is bounded, reported and operator-actionable. `SLOT_MAGIC`'s trailing version nibble tracks the constant (`0x4C56544D4C4E0002`), so a slot whose two disagree is damage rather than another build's generation, which is the `FORMAT_RESET` disposition rather than the block.

What went with the decoder:

- `LiveViewCheckpointMutationArena.putAnchor`, whose only caller was the anchor-root builder.
- The reader's whole legacy arm - `validateAnchor`, `restoreAnchor`, `RestoreAnchorVisitor`, `ValidateAnchorVisitor` and the `isFusedStateRoot` tagged-union flag. `validateState` now decodes the state root strictly (`windowRoot.of`), so a page of any other kind raises out of the window root's own decode; `restoreRuntime` keeps one order, state root then function roots, which is the order a runtime-only member needs.
- `LiveViewWindow.beginLegacyComponentRestore` / `endLegacyComponentRestore` - the upgrade adapter that hoisted a legacy per-function root into a fused runtime - and `restoreCheckpointEntry`, the anchor-only entry restore. `hoistComponentInto` stays; `adoptWindowStatePlan` still uses it.
- `LiveViewCheckpointRoot`'s `anchorRootRef` is now `stateRootRef`, and its validation message names a window state root.

`LiveViewCheckpointWindowRoot.ofIfWindowRoot` survives on purpose. A *probe* - a seal asking whether a predecessor is one it may build incrementally on top of, a test asking what shape a head carries - has an ordinary answer for "no"; a *restore* does not, and uses `of`.

**What the bump did to the three released fixtures, and what their tests now assert.** `lv_checkpoint_10_0_1.zip`, `..._shapes.zip` and `..._extrema.zip` are whole database roots an unmodified 10.0.1 build wrote. All three declare format version 1, so all three now block, and their three test classes are rewritten from "this restores" to "this blocks, keeps every file, keeps serving its rows, and the operator's re-CREATE is the way out". Each case runs that exit as an operator would: `SHOW CREATE LIVE VIEW`, `DROP LIVE VIEW`, re-execute the emitted DDL, then assert the re-created view matches a from-base recompute, seals under version 2, and restores off its own ladder on the next restart.

Four things worth keeping from that rewrite:

- **`LiveViewCheckpointReleaseCompatTest` is the only case that blocks on a version no test wrote.** `LiveViewCheckpointForwardCompatTest` stamps its own superblock; a block that only ever fired on bytes the suite forged would say nothing about a real upgrade.
- **`LiveViewCheckpointReleaseShapesCompatTest` now carries the argument for a timeline-wide boundary.** Four of its five views are unanchored - bounded `ROWS`/`RANGE`/`DECIMAL`, plus a spliced timeline - so 10.0.1 wrote them no state root at all and this build could read every page they hold. They block anyway, because the boundary is the timeline's declared version rather than the shape of the roots under it.
- **`LiveViewCheckpointReleaseExtremaCompatTest` inverted.** It used to pin the cost of the `max`/`min` state-version bump: the released ladder was silently retired and the window recomputed from the base, with the view valid and no fault counted the whole way. The timeline-wide block now fires first, above the function directory, so that silent restatement is no longer reachable through a released tree. The case pins the block *and the absence* of the rebuild's log lines.
- `LiveViewCheckpointWireFormatTest`'s anchor-root case keeps its longhand reading of the released bytes and drops the decoder comparison it can no longer make. What it audits now is that no decoder of this build claims those pages: the probe declines, and the strict decode complains about the page kind rather than about damage.

A blocked directory is unreadable from this build's own tooling as well, which is worth knowing when writing a test against one: `LiveViewCheckpointMetaStore` adopts no generation, so `countSealedBoundaries` and `isFusedHead` raise rather than answer. A file count is what states preservation there, and the rows are compared against a snapshot taken before the catalogue load rather than against a recompute - a recompute being the thing a block must not have run.

### Single-slot format damage, implemented

This was the second of the two items the previous handoff left open. `LiveViewCheckpointSuperblock.foreignFormatVersion()` returned the first slot in the magic family whose version field differed from this build's, without a checksum and regardless of the other slot. So one flipped bit in one slot's four-byte version field blocked the view and cost the operator a `DROP`/re-CREATE, even with the other slot intact. The defect had a second half the handoff did not name: a flipped bit in the magic's version nibble (its low 16 bits) reached `isForeignFormat()`, which condemned the whole directory on one foreign-looking slot. The view then took `FORMAT_RESET` and a whole-view rebuild from whatever base rows survive today, which is one of the silent-restatement doors in the next section. Both halves are fixed.

**The rule.** A slot *declares* a format only when it names the version twice, in the version field and in the magic's nibble. Every build stamps both. `SLOT_MAGIC` tracks `SLOT_FORMAT_VERSION`, and the released 10.0.1 build did the same: all seven released fixture timelines carry nibble 1, version 1 and a valid CRC in both slots, checked byte by byte. The `SLOT_MAGIC` javadoc already called a slot whose two fields disagree damage, and the probes now follow that stated contract:

| Slot contents | Disposition |
| --- | --- |
| Either slot declares a foreign version (both fields agree) | Block, whatever the other slot holds - unchanged |
| A family slot with a non-native magic or version that declares nothing (the two disagree), beside a slot `select()` accepts | Neither block nor reset. A/B selection falls back to the intact slot exactly as after a torn write, and the next seal overwrites the damaged slot |
| The same damage with no selectable slot beside it | Reset. Unchanged for magic damage; **was a block** for version-field damage |
| This build's own magic and version over a stale checksum (a torn write) | Unchanged: selection falls back |

`isForeignFormat()` gained the "no selectable slot" condition through `hasSelectableSlot()`, which reads each slot through the descriptor, because the probes run before anything may create or extend the file. It checks each slot with `isSlotImageValid()`, the predicate `select()` uses, factored out of the instance `isSlotValid()` so the two cannot drift apart.

**Why not the rules the previous handoff suggested.** It proposed "requiring both slots to agree on a foreign version, or requiring that no slot reads as valid-native". Both would unblock the one mixed directory the block exists for. A newer build that published once over this build's directory leaves its own slot, declaring version 3, beside this build's older slot, which is valid and native. Either suggested rule falls back to the native slot there. Reconciliation would then hand the newer generation's segments to `purgeUncataloguedSegments` and its slot to the next publication, destroying the state a return to the newer build needs - and "an accidental downgrade is recoverable by going back" rests on exactly that state. The two-field rule separates the cases by what the slot itself says rather than by what its neighbour holds: one flipped bit cannot make a slot name a foreign version twice, and another build's slot always does. `LiveViewCheckpointLifecycleTest.testADeclaredVersionBesideAnIntactSlotStillBlocks` pins that the mixed directory still blocks and keeps the newer generation's segment.

**What it costs.** A lone slot damaged in its version field used to block and now resets, then rebuilds from the base. "Lone" means a timeline with one published generation, or one whose other slot is torn as well. Checksum damage anywhere else in the same slot already had that outcome (a restore that finds no valid slot fails into the applied-base rebuild), so the version field no longer gets special treatment. It does mean this damage now reaches the whole-view rebuild, which is the open item below. The fallback is also silent. Like a torn slot, a rotted format field is stepped over without a log line of its own: the restore log line names the generation it came back on, and the next seal heals the slot.

**Tests.** In `LiveViewCheckpointSuperblockTest`:

- `testNoSingleBitFlipInOneSlotBlocksOrResetsWhileTheOtherIsIntact` flips every bit of both slots in turn (3,328 flips), and requires that neither probe claims the file and that selection lands on the other slot.
- `testADamagedFormatFieldBesideASelectableSlotIsNotAForeignFormat` does the same for a single field rewritten deliberately and checksummed.
- `testADamagedFormatFieldWithNoSelectableSlotStillResets` pins the cost above.

`LiveViewCheckpointLifecycleTest.testADamagedVersionFieldInOneSlotFallsBackToTheOther` and `...MagicNibble...` pin the reconcile disposition and the heal on the next publication.

`LiveViewCheckpointForwardCompatTest.testAFlippedBitInTheNewestSlots{FormatVersion,MagicNibble}FallsBackToTheOtherSlot` run the whole path on a real view. Each flips bit 0 of the field's low byte in the newest slot, which turns 2 into 3 - the next format version, read alone. It then restarts and asserts `timeline_restore` off the intact slot's generation with zero rebuilds and resets, and correct rows. Finally it commits a row, seals over the damaged slot, restarts off the new generation, and checks that both slots are native again on disk.

As a negative control, all eight damage-path cases fail with the old superblock code swapped back in: the version flip blocks the view and the nibble flip resets the directory. The declared-version, mixed-directory and release-fixture cases pass under both.

Three forgery helpers changed with it, because they wrote the one-field shape the rule now calls damage: `LiveViewCheckpointForwardCompatTest.setSuperblockFormatVersion`, `LiveViewCheckpointLifecycleTest.bumpTimelineFormatVersion`, and the superblock test's declaring stamps (`declareFormatVersion`). All three now write the magic's nibble alongside the version field, which is what a real build of that version writes.

### Rebuild restatement guard, implemented

This was the one open item. Every route into the whole-view rebuild from the applied base now passes `LiveViewRebuildRestatementGuard` before its replacement commits. A rebuild the guard can show would drop rows the view retains is refused, and the view stops with `checkpoint_recovery_phase` `rebuild_blocked` instead of being recomputed from the base rows that survive today.

**Where it sits.** The seven doors reach three callers: `rebuildTimelineRecoveryFromAppliedBase` (restart - an absent timeline, which is where `FORMAT_RESET` and a history-epoch replacement land; a failed restore; a live repair marker), `rebuildActiveWindowStateFromAppliedBase` (base metadata drift, mid-drain failure) and `rederiveFromAppliedBaseAfterWalLoss`. All three funnel into `o3HeadMissReplay(..., fullRebuild=true)`, so the guard lives there, once, rather than at each door. Since the running-door restore, the drift and mid-drain doors reach `rebuildActiveWindowStateFromAppliedBase` only when the restore from the timeline declined or failed.

**The two checks.** Both rest on two properties CREATE enforces for every live view: the output's designated timestamp is the base's designated timestamp column, passed through unchanged (`CairoEngine.validateLiveViewTimestamp`), and every base row the filter admits produces exactly one output row.

- *History floor*, in the rebuild's prologue, before the retire, the wipe or the scan: the view's table holds a row below the pinned base snapshot's earliest row, or holds rows while the base holds none. It reads two row counts and two minimum timestamps off the transaction files, nothing more. TTL eviction and DROP/DETACH of the oldest partitions produce exactly this, so a restart of a view in that state is refused without paying the recompute.
- *Row shortfall*, after the scan and before the commit: the recompute emits fewer rows at or below the view's durable frontier (its table's maximum timestamp) than the table holds. This catches a dropped or detached middle partition, which leaves the base's earliest row where it was. It costs one comparison per emitted row.

**What moved to make the second check safe.** A full rebuild used to retire its timeline at the top of the replay, before the scan. It now retires in `prepareWholeViewReplacement`, after the shortfall check and just before the commit, so a refusal after the scan leaves the timeline standing. Nothing between the old and new positions reads the head or the timeline, and the retire still precedes the commit, so a crash between the two ends where it always did. A crash during the scan now finds the timeline intact rather than retired and restores from it, which is correct because nothing durable moved. The history floor runs ahead of the old retire position as well.

**The disposition.** The refusal throws `LiveViewRebuildRefusedException` - a flyweight, and not a `CairoException`, so no catch arm that counts, retries or invalidates takes it. The replacement is uncommitted, and closing the writer rolls it back. Each of the three callers catches it and calls `blockRefusedRebuild`, which stamps `LiveViewCheckpointRecoveryPhase.REBUILD_BLOCKED` with a reason naming the door (`[cause=timeline is absent]`, `prefix preservation repair marker present`, `base table metadata change`, `mid-drain refresh failure`, `base WAL segment missing`), the evidence, and the operator's ways out. The restart door also records the new `rebuild_blocked` route. From there the view behaves like a format-blocked one: refresh declines it ahead of every other guard, `WalPurgeJob` releases its base WAL floor, and `live_views()` reports `view_status` `invalid` and mirrors the reason through `invalidation_reason`. `isCheckpointRecoveryBlocked()` now answers for both phases and `isCheckpointFormatBlocked()` for the format one, which is the only one the refresh gate records `upgrade_blocked` for.

It is not a durable invalidation - the WAL-loss door reports the refusal to its caller as handled for exactly that reason - and it is not persisted. A restart re-derives it by running the same recovery. A view stopped at a running door reached the rebuild because its in-process restore declined or failed, so the restart's restore meets the same obstacle unless it was transient; when it restores, the view resumes with the history the base lost still in it. A view stopped at a restart door meets the same refusal.

**When it compares nothing.** The checks read the view's table as the output of the base transactions the view has consumed, while the rebuild runs at a pinned snapshot `E` that may hold more. The guard abstains, and the rebuild runs exactly as before, when:

- `cairo.live.view.rebuild.restatement.guard.enabled` is off (it defaults to on), or the view's table is empty;
- ~~`E` is behind the view's own coordinate, the highest of the applied watermark, the processed watermark and the lead. A raw-WAL drain can run ahead of the base's apply, and its output would otherwise read as a loss;~~ **Closed.** No rebuild pins a snapshot behind the rows the view's table holds any more, the lead no longer counts toward that point, and the abstention is deleted; see "Snapshot floor, implemented";
- the backlog `(appliedWatermark, E]` holds a commit that can legitimately lower the output at or below the frontier: a REPLACE_RANGE whose delete band reaches it (a materialized-view base), a materialized view's TRUNCATE, or - for a filtering view - any commit on a deduplicating base that reaches it, whose replacement row can fail the filter. Incremental refresh propagates all three, so following them restates nothing;
- the backlog cannot be read (a lost WAL segment) and the base can produce one of those commits. Any other base is compared anyway: REPLACE_RANGE reaches a table only through a materialized view's refresh, since a live view's own table cannot be a live view's base, and a filter flip needs dedup.

UPDATE on a base invalidates the view on the apply side and never reaches a rebuild. TRUNCATE, DROP/DETACH PARTITION and TTL eviction are the removals the guard exists for, so none of them stands it down. When the guard stands down over a view that has rows to lose (a backlog that may remove rows, an unreadable backlog; a lagging snapshot too, until the snapshot floor), the rebuild logs `live view rebuild from the applied base runs without the restatement guard` with the reason, so a restatement found afterwards has a line explaining why nothing stopped it.

**What it cannot see**, stated because the previous handoff asked for it. The checks detect restatements; they do not prove there are none, for the reason "Why the compatibility policy was withdrawn" gives. They pass:

- a loss that keeps the row count: the base and the view's own table lost the same prefix, as matched TTLs leave them, so the retained rows' accumulated values change and their count does not;
- a loss masked by backlog inserts at or below the frontier;
- anything in a backlog the guard abstained over. A rebuild whose snapshot is behind the view was on this list too, until the snapshot floor made it unreachable.

A dedup flag disabled inside the backlog, after commits that used it, reads as non-deduplicating. That can refuse a rebuild that would have been legitimate; a restart retries it.

**A correction to the premise.** The previous version of this section called a view without checkpoint support the commonest case a blanket block would stop, since such a view rebuilds on every restart by design. No such view can be created on this branch. `CairoEngine.validateLiveViewWindowFunction` rejects any window function whose `supportsCheckpointState()` is false (unless it is checkpoint-stateless), and that predicate folds in the anchor key codec, so an unencodable partition-key type is rejected at CREATE as well (`LiveViewInMemReadTest` says the same). Every view seals its first boundary when its first row lands. "Timeline is absent" with rows in the table therefore means a directory reset for its format, a history-epoch replacement, or a timeline an earlier failure retired - never a view built to rebuild on every restart. The switch stays as an escape hatch for an operator who would rather a view track its base's retention than stop.

**Costs.**

- A view that would have been restated silently now stops and needs an operator: a restart (while the base WAL lasts, and only where the restart's restore can run), `DROP` and re-CREATE, or the switch. That is the policy the rest of this document chose, and it is a behavior change on upgrade for every view in that state. The running doors reach the refusal only when their in-process restore could not run, which takes most of this cost off them.
- The row-shortfall refusal pays the whole recompute scan before it refuses, and a restart door pays it again on every restart of a view it blocked, since nothing records the block. The floor is O(1) and catches the common case first.
- The released WAL floor has the price the format block's has: a running-door view whose block outlives a purge sweep can no longer restore from its timeline, and its restart meets the rebuild and the same refusal.
- A view stopped at a running door keeps serving its in-memory tier's un-flushed lead rows, because readers take the lead from the slot rather than from the instance's count. A restart drops them, as a crash would.

**Tests.** `LiveViewRebuildRestatementGuardTest`, ten cases as first written (eleven since the running-door restore, fifteen since the snapshot floor, seventeen since the deferred-rebuild report; see those sections):

- a restart with no timeline over a base that lost its oldest day: refused on the floor with no row scanned, the `rebuild_blocked` route, rows and watermark unmoved under a new base commit, the same disposition on a second restart, `live_views()` reporting it, and the re-CREATE exit;
- a restart behind a live repair marker over a base that lost a middle day: refused on the shortfall (4 of 6), the replacement rolled back, and the marker, generation and ladder exactly as the crash left them;
- a base schema change on a running view - a dedup collapse routes the drain through the applied base, where the stale plan meets the drift: refused, the timeline's generation and ladder unchanged, and a restart restores from it (`timeline_restore`) with the dropped day still in the view and the commit that arrived while it was stopped materialized on top. **Superseded** by the running-door restore: the same drift now restores in process and is never refused; the refusal at this door is covered by a variant with a live repair marker in front of the timeline;
- a lost base WAL: refused on the floor rather than invalidated, the guard comparing over an unreadable backlog because the base cannot hide a legitimate removal;
- a complete base: the rebuild goes ahead, compared, reproducing all six rows;
- a deduplicating base under a filter, with an unconsumed replacement that fails the filter: the guard abstains (`backlog may remove rows`) and the rebuild removes the row;
- the switch off: the rebuild follows the base and drops the day;
- three narrow cases on the guard's contract: abstentions compare nothing, the floor is strict and covers an empty base, and the shortfall counts only rows at or below the frontier.

The whole `cairo/lv` package passes with the guard in, at 2,040 tests; no existing case needed a change, which is the evidence that the abstentions keep the rebuilds that heal today running. Negative controls, each run against the new class: with the floor disabled the three floor cases fail; with the shortfall disabled the marker case and the shortfall contract case fail; with the retire moved back ahead of the scan the marker case fails (the floor refuses in the prologue, ahead of the old retire position, so only the shortfall path depends on the move); with the dedup-filter abstention removed the backlog case fails. `LiveViewDedupBaseTest.testRestartRebuildPurgesBelowFrontierDedupReplacement` passes under that last mutation too, because its restart takes the restore route, which is why the backlog case exists.

### Running-door restore from the timeline, implemented

This was the first of the three items the guard's handoff left open, and the one that shrinks the guard's cost; it landed as commit `f296b42b4f` ("Restore a running live view from its timeline") and is written up on PR #6939 as the eighteenth round. The base-metadata-drift and mid-drain-failure doors no longer go straight to the whole-view rebuild. Each first runs the restart's own recovery in place: it recompiles the view's SELECT at identity, restores the newest compatible timeline root, and replays the base WAL between that root and the applied watermark. Only when that restore declines or fails does the door fall back to the rebuild, and only there can the guard refuse it.

**Why it is sound.** Both doors leave the view's durable output correct and only its runtime wrong: a drift freed the compiled factory and its accumulators with it, and a mid-drain failure fed rows the turn never committed. The timeline describes the runtime at a boundary at or below the durable frontier, and `WalPurgeJob` holds the base WAL back to the head checkpoint's base commit and the timeline's floor, so the WAL the replay needs is retained. The replay rewrites no output, so it cannot restate anything, and the rows the base lost do not enter into it. This removes the commonest refusal instead of reporting it: a view whose base lost a day, and which then meets a base schema change or a mid-drain fault, keeps refreshing with that day still in it.

**Where it sits.** `LiveViewRefreshJob.recoverActiveWindowState` is the new front of both doors: `tryRestoreRuntimeFromTimeline`, then `rebuildActiveWindowStateFromAppliedBase` if that returns false. The restore itself is `restoreFromTimeline`, extracted from `tryRestoreFromTimeline` so the restart and the running doors share one implementation of root selection, corrupt-root healing, the replay to the applied watermark, the durable row-count and frontier check, and the head checkpoint stamp. The two callers differ only in what they record. The restart names the root in its route witness; a running door bumps the new `LiveViewInstance.getCheckpointRuntimeRestores()` counter, logs `live view restored its runtime from the checkpoint timeline [view=..., cause=..., replayedRows=...]` and leaves the restart route alone. Both use `isRepairMarkerLive`, which the marker check moved into. `LiveViewInstance.prepareForBaseSchemaRecompile` is renamed `prepareForRecompile`, since the restore is its second caller. `rebuildWindowStateAfterMidDrainFailure` is renamed `recoverWindowStateAfterMidDrainFailure`.

**What the soft restart resets** - the instance state the previous handoff named:

- compiled factory: freed and recompiled at identity (`prepareForRecompile`, which also discards a parked repair, frees the anchor window, the isolated repair runtime, the stored-row scan and the copiers, and clears the head root identity);
- head checkpoint: `restoreFromTimeline` stamps it from the restored root with `writtenUs` null, exactly as at a restart, so the first flush after the restore seals;
- lead: dropped before the restore, because the out-of-order hand-off inside the replay expects none, and `refreshedUpToSeqTxn` pinned to the restored watermark afterwards, so the next drain derives those rows again;
- tier: restaged from the view's table through `rebuildInMemoryTier`, which also drops the symbol cache's stale intern entries;
- window-state debt: cleared on success, unless the replay handed off to an out-of-order repair that parked, which then owns the runtime.

**When it declines** - returns false with the runtime untouched, and the door rebuilds as before:

- the view's table does not hold every block its own WAL committed (a pending out-of-order replacement, or a flush whose inline apply has not landed);
- the timeline is absent;
- a live prefix-preservation repair marker stands over it, so its superblock may still name a truncated head.

The restart rebuilds in all three cases too. A restore that starts and then fails - no compatible root, corrupt roots it cannot heal, a replay that does not reproduce the durable row count and frontier - also returns false. It does not discard the half-restored runtime, because nothing reads it: the full rebuild resets the runtime to identity on both its row and its no-row branch, and a rebuild that fails before that leaves the debt for the next turn's gate, which recompiles before it restores. The restart's own fallback leaves the same half-restored runtime to the same rebuild. A first cut did discard it; with the discard removed as a mutation no test changed outcome, and the reasoning above says none can. A cancellation ends the recovery without the fallback.

The WAL-loss door is left out on purpose. Its missing segment sits above the applied watermark, so a restore would succeed and the next drain would fail on the same segment; only the rebuild gets past it. Its drift retry calls the rebuild directly (`recoverFromBaseMetadataDrift(instance, false)`).

**A latent defect fixed on the way.** The drift door freed the compiled factory, and the next factory use compiled one at identity, but nothing marked the runtime as owing a recovery. When the drift's recovery failed before the rebuild's wipe - the rebuild's probe read, `waitForApply`, the guard's transaction-file reads - the next turn drained forward through that identity runtime and committed accumulations restarted from zero, with the view valid and no further fault. `recoverFromBaseMetadataDrift` now marks the window state dirty before it recovers an ACTIVE view, so a failed recovery leaves the next turn's gate to settle the debt. `LiveViewRuntimeRestoreTest.testADriftWhoseRecoveryFailsLeavesTheDebtForTheNextTurn` pins it: without the mark, acct-1's day-three row reads `64.0` over one row instead of `80.0` over two. The defect predates the restore - the drift door's rebuild could fail before its wipe just the same - and surfaced while working out which debt the soft restart has to settle.

**A second edge closed, in the restart as well.** A restore's replay hands off to `o3Replay` when it meets an unresolved out-of-order commit (a post-O3 seal that failed), and a localized repair there can park on its turn budget. The restart turn used to carry on to the gate and the drain over the runtime that repair stands in. It now ends the turn when a repair is parked after the restart restore, and the gate does the same after a running restore. **Neither check has a test**: reaching it needs a failed post-O3 seal and then a replay long enough to exhaust the turn budget inside a restore.

**Costs.**

- A running-door recovery now costs a recompile and a replay of the base WAL above the head root, where it used to cost a full recompute of the view. At the default cadence (a root every million rows or five minutes, tightened by the adaptive cadence after corrections) that replay can cover up to five minutes of base commits, read from raw WAL rather than the applied table.
- The rebuild committed through the base's applied seqTxn in the recovery turn itself. The restore stops at the view's own applied watermark, and the next turn drains the commits above it - into the lead for a lead-eligible view, flushed on the `FLUSH EVERY` cadence. `LiveViewSmokeTest.testMidDrainRefreshFailureRecoversWindowState` asserted the rebuild's watermark jump and now asserts `refreshedUpToSeqTxn` instead.
- A lead-eligible view's un-flushed lead leaves the tier when the restore drops it and returns when the next drain derives it again. A reader in between sees the durable rows without the lead, as after a restart; the rebuild had no such gap, because it committed through the base's head in the same turn.
- A deduplicating base whose replay gap holds a commit the base deduplicated fails the restore's row check and falls back to the rebuild, as it does at a restart. `testARestoreThatCannotReproduceTheViewFallsBackToTheRebuild` pins the fallback.
- A debt carried from a drift is recovered by the gate under the cause `mid-drain refresh failure`, the label the gate has always used for any carried debt. The log line is less precise than it could be; nothing reads the cause except logs and the refusal reason.

**Tests.** `LiveViewRuntimeRestoreTest`, six cases, each at the default cadence so every restore has WAL to replay above its root:

- a base schema change on a deduplicating base: restored with `replayedRows=5`, no rebuild started and no timeline retired, the colliding commit materialized on top, and a restart restoring from the same ladder;
- a mid-drain failure with an un-flushed lead at the moment of the fault: the lead dropped, the three interrupted commits derived into the lead again (`leadRowCount` 3) over the restored runtime before any flush, `replayedRows=3`, no retry charged, and correct rows through a restart;
- a mid-drain failure over a base that lost a day: restored rather than refused, the guard never armed, the dropped day kept;
- a live repair marker: the restore declines, the rebuild covers, and its retire takes the marker with the timeline;
- a replay that cannot reproduce the view (a deduplicated commit in the gap): the restore's own check refuses it and the rebuild covers;
- a drift whose restore and rebuild both fail: the debt carries and the next turn's gate restores.

`LiveViewRebuildRestatementGuardTest` has eleven cases. Its drift case now asserts that the restore keeps the view refreshing with the dropped day, and a new case puts a live repair marker in front of the same drift to keep the running-door refusal (`cause=base table metadata change`) covered, through a restart that meets the marker's own refusal. `LiveViewSmokeTest`'s two mid-drain cases are renamed for the recovery rather than the rebuild, and the one whose recovery fails now fails the restore's timeline open as well as the rebuild's scan.

Negative controls, each run against the new code and then restored: with the restore disabled, ten of the twenty cases in those three classes fail; without the drift door's debt mark the debt case fails on its rows; without resetting `refreshedUpToSeqTxn`, or without zeroing the lead count, the two lead-carrying mid-drain cases fail; without the marker check both marker cases fail. The parked-repair checks have no negative control, for the reason above.

The whole `cairo/lv` package passes at 2,047 tests in 134 classes. The first full run with the restore in, before any test changed, failed exactly the three cases that asserted rebuild-specific side effects at these doors and nothing else.

### Snapshot floor, implemented

This was the second of the items the running-door restore's handoff left open: "the snapshot-behind abstention leaves one rebuild of a view whose raw-WAL drain leads the base's apply unguarded. Waiting for the apply to reach the view's coordinate before rebuilding would close it, at the cost of moving the rebuild's commit point." It is closed, and working it out changed what "the view's coordinate" means. It landed as commit `e62afd28ff` ("Wait for the base apply before rebuilding a view") and is written up on PR #6939 as the nineteenth round.

**What the abstention was actually catching.** The guard stood down whenever the pinned snapshot `E` was behind the highest of the applied watermark, the processed watermark and the lead's (`refreshedUpToSeqTxn`). The running doors pinned the base's applied head (`getTxnTracker(base).getWriterTxn()`), and a lead-eligible view drains raw WAL into its lead as soon as a commit is sequenced, well before `ApplyWal2TableJob` applies it. So the abstention fired on the ordinary lag between a view's lead and its base's apply - the common case under ingestion, not an edge - and in each such case the rebuild ran unchecked and committed at `E`, which moved the view's processed watermark backwards whenever the view had flushed past it. A negative control against the previous code reproduces it: a mid-drain failure behind a live repair marker, over a base that lost a day, logs `runs without the restatement guard [reason=snapshot behind the view]`, pins seqTxn 7 behind a lead at 8, and removes the lost day's partition from the view.

**The floor.** `LiveViewRefreshJob.rebuildSnapshotFloor` is the highest base transaction whose output the view's **table** may hold: the higher of the applied and processed watermarks. The lead no longer counts, for three reasons that each hold on their own. Its rows sit in the in-memory tier until a flush moves the processed watermark over them; the guard reads only the table (`lvReader.size()`, min and max timestamp); and every rebuild door drops the lead before it commits, so the next drain derives it again from wherever the rebuild left the view. The one way found for the table to hold output past the processed watermark is a commit whose WAL writer then fails to close, before the in-memory watermark is set. Against a snapshot that lacks those rows the checks can only refuse a rebuild, never let a restatement through, and the lead's watermark would not have covered that edge for a coupled view anyway, whose lead and processed watermark move together. Taking the lead out of the floor is what makes most of the old abstentions disappear without any waiting: a view whose lead alone runs past the base's apply now has its rebuild compared at once.

**Where the waiting happens.** Only when the view has *flushed* output of commits the base has not applied - its processed watermark is past the base's applied head - does a rebuild need to wait, and only the running doors can meet that:

- *Running doors.* `rebuildActiveWindowStateFromAppliedBase` pins `max(base applied head, floor)` and first calls `ensureBaseAppliedForRebuild`. It reads the tracker and, only when the tracker says the base lags, confirms against a base `TableReader`, since the tracker can trail the durable `_txn`, reads `-1` until an apply warms it and again after `notifyWalTxnRepublisher` resets it. A confirmed lag throws `LiveViewApplyLagException` before anything moves - ahead of zeroing the lead - so the tier and every watermark stay as they were and the window-state debt stands. The deferral is cooperative, not a blocking `waitForApply`, because the single-threaded harness applies the base on the same thread and a frozen clock never trips the wait's budget.
- *Who catches it.* A recovery run from the refresh turn's own window-state gate propagates to `refreshInstance`'s existing apply-lag arm, which re-marks the debt and arms the back-off. A recovery run from `handleRefreshFailure` - the drift door and the mid-drain door - executes inside `refreshInstance`'s catch clause, which that arm cannot reach, so `handleRefreshFailure` has an arm of its own for each: arm the back-off, carry the debt (the mid-drain one only lived in the turn's field until then), charge nothing, return. `armApplyLagDeferral` is the arming both places share, factored out of the old inline code.
- *Retry.* The existing back-off paces it: `isApplyLagDeferred` releases the view the moment the tracker reaches the target, or after the 5 ms floor. The next turn's gate recovers the debt again, restore first, and the rebuild runs once the base has caught up. It commits at the base's head at that point, past the view's own coordinate - the commit point moves forward, materializing commits the view had drained, rather than backward as before.
- *Logging.* `live view rebuild from the applied base waits for the base table to apply what the view consumed [view=..., cause=..., rebuildSeqTxn=..., appliedSeqTxn=...]` at INFO, once per target: a retry that defers on the same target (the one `getApplyLagDeferTargetSeqTxn` already holds) stays quiet. The top-level arm's own DEBUG line now reads `live view refresh deferred, base apply lag`, since it no longer covers O3 replays only.

The other two door families need no deferral:

- *Restart doors* pin the applied watermark they restored, which is the floor at a restart (the two watermarks are persisted together), and keep the blocking `waitForApply` they always had. The pinning overload of `o3HeadMissReplay` raises every full rebuild's pin to the floor anyway, so the invariant holds by construction rather than by that argument.
- *WAL-loss door.* `rederiveFromAppliedBaseAfterWalLoss` already refused to run unless the base had applied past the processed watermark; its precondition now reads the floor, which on a primary is the same thing, so it never pins behind the view and never defers. Its drift retry calls the rebuild directly and meets `ensureBaseAppliedForRebuild` on the same precondition, which the base's monotone `_txn` always satisfies.

**The invariant.** `armRebuildRestatementGuard` asserts `effectiveSeqTxn >= rebuildSnapshotFloor(instance)` where the abstention used to be, and `LiveViewRebuildRestatementGuard.ABSTAIN_SNAPSHOT_BEHIND` is deleted (the two backlog abstentions renumber to 3 and 4; nothing persists them). If the assertion were ever false in production, the checks would compare anyway, which errs toward refusal: a snapshot missing commits the table has output of reads that output as a loss.

**Costs.**

- A running-door rebuild over a view that flushed past its base's apply now waits for the apply, where it used to run at once, unchecked. Normally that is the apply's own lag, milliseconds to seconds. A base whose apply is suspended or stalled below the floor keeps the view deferred - not refreshing, not invalidated, and not reported through `live_views()` - until the apply reaches it; the one INFO line and the view's lag behind its base are the trace. The O3 replay's deferral has had the same property all along. **Since reported** for the rebuild, though not for the O3 replay: see "Deferred rebuild reported, implemented".
- Every retry while deferred re-runs the restore attempt before it reaches the rebuild. The restore's declines (a live marker, an absent timeline, a table that trails its own WAL) are file probes. A restore that starts and fails - a deduplicated commit in the replay gap - cannot meet a deferral, because a view over a deduplicating base drains the applied base and never flushes past its apply.
- A debt carried from a drift door that deferred is recovered by the gate under the cause `mid-drain refresh failure`, as any carried debt already was, so a refusal after the wait names that cause rather than `base table metadata change`.
- **The drift door's deferral arm in `handleRefreshFailure` has no test.** Every path that surfaces a base schema change as drift reads the applied base - the dedup drain, an O3 replay - and gates on the base's apply first, so no case was found that reaches the drift door with the view flushed past the apply. The arm is there so that a deferral from it would defer rather than escape `refreshInstance`. The mid-drain arm beside it and the gate path are both witnessed.

**Tests.** `LiveViewRebuildRestatementGuardTest`, four new cases, fifteen in all:

- `testARebuildBehindTheViewsLeadComparesAtOnceAndRefuses`: three commits the base has not applied, the first drained into the lead, the fault failing the pass over the next two; a live marker keeps the restore off the timeline. The rebuild pins where the base had applied, compares without waiting, and refuses on the history floor.
- `testALostBaseWalRederiveBehindTheViewsLeadComparesAndRefuses`: a lead one commit past the base's apply, a third commit written through a second WAL that is then removed, the retry budget spent on it (driven by re-publishing the base head, because the fallback scan drives a view only as far as the base has applied). The re-derive compares at the base's head and refuses, where it used to stand down and restate.
- `testARebuildAheadOfTheBaseApplyWaitsForItAndRefusesToDropTheOldestDay`: the view flushes a commit the base has not applied, then fails mid-drain over three more. The rebuild defers - asserted as the log line with both seqTxns, the debt, the back-off target, one fault, no retry charged, no snapshot pinned - and a retry once the back-off elapses, with the base still behind, defers again through the gate and the top-level arm without a second log line. After the base applies, the guard compares and refuses, with the timeline, marker and watermark intact.
- `testARebuildAheadOfTheBaseApplyWaitsForItAndHealsACompleteBase`: the same over a base that lost nothing. After the apply the guard compares, reproduces all seven rows, and the rebuild commits four commits past where the base stood at the fault.

`LiveViewMidDrainFault`, the one-shot WAL column read fault, moves out of `LiveViewRuntimeRestoreTest` so both classes share it.

Negative controls, each run against the guard class and then reverted:

- the previous code fails exactly the four new cases (15 run, 4 failed);
- counting the lead in the floor again fails all four: the lead-only running door defers where it should compare, the flushed-ahead ones defer on the lead's seqTxn rather than the flushed one, and the WAL-loss door takes its old exit (`budget exhausted, invalidating`);
- dropping the wait - no deferral, no raised pin, no assertion - fails the two flushed-ahead cases;
- removing `handleRefreshFailure`'s mid-drain arm lets the deferral escape `refreshInstance` and errors both flushed-ahead cases;
- leaving the debt off the instance in that arm fails both on `isWindowStateDirty`;
- letting the rebuild's catch-all swallow the deferral as an ordinary failure fails both on the back-off target that is then never armed.

One mutation survives the guard class, as expected: dropping the top-level arm's re-mark of the debt. A debt the gate recovers already lives on the instance; that re-mark exists for an O3 drain's per-turn debt, which predates this change, and `LiveViewConcurrencyTest.testApplyLagDeferralRebuildsAdvancedWindowState` fails under the same mutation on exactly that debt.

The whole `cairo/lv` package passes at 2,055 tests in 134 classes: the running-door restore's 2,047, four from the merge of `master` that came in after it (`LiveViewStartFromSeedRestartTest`), and the four above.

### Deferred rebuild reported, implemented

This was the third of the items the snapshot floor's handoff left open: "A deferred rebuild is not reported. A running door that waits for its base's apply shows up only as one INFO line and the view's lag behind the base ... a base whose apply is suspended keeps the view waiting indefinitely with nothing in `live_views()` to say so. A phase or column naming the wait would make it an operator-visible state like the two blocks." It is closed with a phase. It landed as commit `ccb1dfc8bf` ("Report a live view rebuild that waits on its base") and is written up on PR #6939 as the twentieth round.

**What an operator sees.** While a running door's rebuild waits for the base's apply, `live_views()` reports `checkpoint_recovery_phase` `rebuild_deferred` and a `checkpoint_recovery_reason` naming the recovery that asked for the rebuild, the base table and the seqTxn awaited:

`rebuilding the view from its base table waits for the base table to apply what the view consumed [cause=mid-drain refresh failure, baseTable=tx, rebuildSeqTxn=7]: the view's table holds output of base commits the base table has not applied yet, and nothing has moved. Refresh resumes on its own once the base table applies seqTxn 7; a base table whose WAL apply is suspended (see wal_tables()) keeps the view waiting until the apply resumes`

`view_status` stays `active` and `invalidation_reason` stays NULL. The view has not stopped, so the queries that find stopped views must not find it; the two recovery columns are where it shows.

**Why a phase rather than a column.** `checkpoint_recovery_phase` already answers "where does this view's recovery stand", and a rebuild waiting for its base is a recovery that has not finished. A third constant, `LiveViewCheckpointRecoveryPhase.REBUILD_DEFERRED = 3`, reuses both columns, changes no `live_views()` schema, and keeps the reason beside the phase. The price is that the phase stops meaning "stopped": `isCheckpointRecoveryBlocked()` now asks the new `LiveViewCheckpointRecoveryPhase.isBlocked(phase)` (`BLOCKED` or `REBUILD_BLOCKED`) instead of `phase != NONE`. Its three readers therefore treat a waiting view as the refreshing view it is - the refresh gate lets it through to the apply-lag back-off, `WalPurgeJob` keeps its base WAL floor, and `LiveViewLifecycleState.derive` reports `ACTIVE`. The floor it keeps is bounded, unlike a block's: the wait ends once the base applies the commit it names, so the applied WAL it holds from purge never runs past that commit.

**Where it is set and where it ends.** All of it on the refresh worker under the refresh latch:

- *Set* by `ensureBaseAppliedForRebuild` on the first deferral of a target, beside the INFO line it already logged, through `LiveViewInstance.markCheckpointRebuildDeferred`. The reason is built once per target in the thread-local sink; the retries the back-off paces keep the same `String`, so a waiting view allocates nothing per retry. The condition is `target changed || phase not deferred`, so a first rebuild deferral on a target an O3 replay's deferral happened to leave in `applyLagDeferTargetSeqTxn` still publishes the phase. **That second half has no test.**
- *Ended* by `ensureBaseAppliedForRebuild` itself once the base is found applied far enough, through `clearCheckpointRebuildDeferred`. The wait is over whatever the rebuild then does: it recovers, it is refused (`markCheckpointRebuildBlocked` replaces the phase), or it fails - the view is charged a retry and still owes the recovery, but no longer reports a wait the base has satisfied.
- *Ended* by `recordRefreshSuccess()`, which covers a retry that restores from the timeline instead of rebuilding.
- *Ended* by `tryFreeRuntimeStateIfInvalid()` and `tryCloseIfDropped()`. Both run under the latch after the last cycle that could still have deferred, and every later cycle returns before its recovery runs, so nothing re-arms it. An invalid view reporting a rebuild that "resumes on its own" would be wrong.
- `markCheckpointRebuildDeferred` never displaces a block. A blocked view's turn is declined before any recovery could defer, so this is defensive.

**Reading the pair.** `LiveViewsFunctionFactory` now snapshots the phase, then its reason, once per row in `of()`, and the reason is NULL whenever the snapshot phase is. Writers put the reason down before the phase and clear it before the phase, so a row never pairs a phase with a reason from before it, and a NULL phase always comes with a NULL reason. What is left is a benign torn read during a transition: a `rebuild_deferred` row carrying the next block's reason, or none. `invalidation_reason` mirrors the recovery reason only for the two block phases, read off the same snapshot.

**Costs.**

- A new value in an existing column. A query that read `checkpoint_recovery_phase IS NOT NULL` as "stopped" now also matches a view that is only waiting; `view_status = 'invalid'` remains the stopped-view test.
- The reason carries the seqTxn awaited, not the base's applied seqTxn, which would have to be rebuilt on every retry. `wal_tables()` gives the live value and the INFO line the value at the first deferral.
- The O3 replay's apply-lag deferral is still unreported. It is the same wait on the same back-off, but it is the ordinary drain rather than a recovery and has no recovery phase to report under.
- Not persisted, and nothing would read it: a restart recovers through its own blocking `waitForApply`, never a deferral, so a restarted view never reports this phase.

**Tests.**

### The drain's apply-lag wait reported, implemented

This was the fourth of the items the previous round left open: "The O3 replay's apply-lag deferral is not reported. It is the same wait on the same back-off, with the same suspended-base hazard, but it happens in the ordinary drain, which has no recovery phase to report under. A report would need a signal of its own - say a column read off `applyLagDeferTargetSeqTxn` while the back-off is armed - and that field would first need clearing on every path that ends the wait." It is closed with two `live_views()` columns and the clearing the previous round named as its prerequisite.

**What an operator sees.** Two new LONG columns, `base_apply_wait_seqtxn` (63) and `base_apply_wait_micros` (64). While a refresh cycle is held back by its base table's apply, the first names the base seqTxn it waits to see applied and the second how long it has been waiting. Both read NULL, as a pair, for a view that waits for nothing - the steady state - and both reset on restart.

A view merely keeping up with a busy base passes through this state constantly, so the presence of a reading says almost nothing and the duration says everything: `base_apply_wait_micros` growing past a few back-off windows is a view that is not going to converge on its own, and `wal_tables()` on the base names the reason (a suspended apply being the one an operator acts on). `view_status` stays `active` throughout and `invalidation_reason` stays NULL: the view is refreshing, just not getting anywhere.

**Why columns rather than a phase.** The deferred rebuild took a `checkpoint_recovery_phase` because it is a recovery that has not finished. This is not a recovery - it is the ordinary drain - and there is no phase for it to be a phase of. Two columns read off the deferral itself cover both cases instead: every apply-lag deferral arms through `armApplyLagDeferral`, whether it came from the O3 replay, the coupled dedup drain, or `ensureBaseAppliedForRebuild` on behalf of a recovery. So a view waiting to drain reports the pair with a NULL `checkpoint_recovery_phase`, and a view waiting to rebuild reports the pair *and* `rebuild_deferred`; the two together say which wait it is. The deferred rebuild gains a duration it did not have, which is the reading its own reason could not carry.

**The episode, not the window.** The back-off floor (`applyLagDeferUntilUs`) cannot be the signal: it ends every `APPLY_LAG_DEFER_BACKOFF_US` whether or not the base applied anything, so a view waiting on a suspended base holds no floor for most of its wait, and a duration measured from the floor would restart once per window - exactly erasing the difference the column exists to show. `LiveViewInstance` therefore carries a third field, `applyLagDeferSinceUs`, stamped by the first deferral of an episode and left alone by every retry. `armApplyLagDeferral` writes the target, then the floor, then the stamp if and only if it is unset.

**Where it ends.** The previous round's note was right that only `recordRefreshSuccess()` cleared the target, and a stale target is now a stale *report*, so the wait is ended everywhere it ends, through one `clearApplyLagDeferral()` that clears stamp, floor and target together:

- *`recordRefreshSuccess()`* - a cycle that drained proves the lag has passed. This is where the previous clear was, now covering the stamp too.
- *`handleRefreshFailure()`*, at the top, beside `recordRefreshFault()` - a turn that reached a fault of its own is failing, not waiting, and a view that reports a commit it is waiting for while it is really failing is wrong twice over. Cleared there rather than at the two call sites because the drift and mid-drain recoveries below it can defer the rebuild they owe, and that fresh wait has to outlive this clear.
- *`tryFreeRuntimeStateIfInvalid()`* and *`tryCloseIfDropped()`*, under the refresh latch, beside the rebuild-deferral clears they already carry: an invalidated or dropped view waits for nothing.

The authoritative under-latch check keeps clearing the floor alone (`clearApplyLagDeferFloor()`). It runs when the window elapses or the base catches up, which releases the *next turn*; whether the view is still waiting is that turn's answer to give, and the episode stands until it gives one.

**Reading the pair.** `LiveViewsFunctionFactory` snapshots the target then the stamp, once per row in `of()`, mirroring the write order (target before stamp on the way in, stamp before target on the way out). Both columns report only when both readings came back non-NULL, so a transition landing between them yields a NULL pair rather than a duration belonging to one episode beside a target belonging to another. `base_apply_wait_micros` is `now - stamp` at read time, like `lag_micros` and `writer_stall_micros`.

**Costs.**

- Two more columns on a 63-column function, and a `SELECT *` shape change. `LiveViewSmokeTest.testLiveViewsCatalogueColumnOrderMatchesRfc` pins the new order.
- The reading is as of the last turn, not as of the query. A base that applied the awaited commit a moment ago still reports the wait until the view's next turn ends it. The turn is not far off - a deferred view has work outstanding, so the scan re-triggers it - but under a paused refresh worker the pair can outlive the wait it describes.

### Why the compatibility policy was withdrawn

The recovery policy specified below rests on the `coverage` field of its recovery bundle: an original, gap-free transaction archive rooted at table creation, including the row payloads of history removed by TTL, DROP/DETACH PARTITION or TRUNCATE.

**QuestDB produces no such artifact and cannot be made to produce one retroactively.** WAL segments are purged once applied. Dropped and detached partitions are not archived. TTL eviction happens inside `TableWriter.enforceTtl()` during a commit and keeps no journal of what it removed. The sequencer's `_txnlog` records structural transactions but not evicted row payloads. As specified, no existing deployment could build a passing bundle from its own data, so every real upgrade would take the blocked outcome and stay blocked - and, with a bundle as the only exit, stay blocked forever while pinning its base table's WAL.

The alternatives were weighed and rejected:

- **Bounded required-history plus an output cross-check.** For an anchored window the state at boundary `T` depends only on the current anchor segment plus function warm-up, so the required range is computable, and the view's own retained output is an independent witness a recomputation can be compared against. Real, but a large amount of new machinery to reach a recovery the operator can already perform themselves with `DROP` and re-CREATE, and it still fails for views whose state dependence is unbounded.
- **A retention journal on the base table.** Recording every history-removing operation would let a preflight prove the negative directly. A new durable per-table structure, touching the TTL path, the ALTER paths and snapshot/restore - and existing tables have no journal, so they block until it has covered the required window anyway.
- **The operator-supplied bundle alone.** Honest about what the database can prove, but a validated import path with no supplier: nothing in QuestDB emits a conforming archive.

What replaces all of it is the decision the document already made for the operator's own re-creation - "a separate operation with changed historical results, not successful completion of this upgrade" - promoted from a footnote to the whole policy. The database stops and reports; the operator decides. See "A blocked view is a stopped view" above.

The one thing this left was the anchor-root **decoder**, and it is now gone too: `LiveViewCheckpointAnchorRoot` and `LiveViewCheckpointAnchorRootBuilder` are deleted and `SLOT_FORMAT_VERSION` is advanced with them, which is what turns a released directory from something this build would misread into something it holds. See "The format boundary, implemented" above. That step was safe precisely because a blocked view is bounded and has an exit.

## Required design [DONE]

### Separate storage planning from runtime binding [DONE]

Today, `LiveViewWindowStatePlan` describes both persisted component layout and runtime accumulator sharing. `LiveViewWindow.build` discards the compiled plan when fusion is disabled, and `getCheckpointWindowStatePlan()` exposes the adopted runtime plan. Writers and readers use that nullable result to choose the on-disk representation.

Introduce an explicit distinction between the storage plan and whether its components are bound into a shared runtime map. The exact class split is an implementation choice. Required behavior:

- The storage plan exists for every anchored window, independently of the fusion setting.
- Its window identity, key schema, component ordering, manifest, and inline width are deterministic for the same compiled query across fusion settings.
- With fusion enabled, freeze and restore continue to use the shared map efficiently.
- With fusion disabled, freeze gathers the same durable component images from the functions' private state, and restore distributes them back into that state using the existing component codecs and projection semantics.
- Shared or derived components must reconstruct every affected projection correctly in the private-map runtime. SUM/AVG/COUNT sharing is an important test case.
- Runtime rebinding preserves live state. Dirty tracking, baseline generation, and logical-byte accounting must remain valid; retaining a storage plan alone does not establish an incremental baseline.

Do not implement this by silently forcing runtime fusion on. The configuration switch must still control runtime sharing.

Audit uses of `plan != null`: after this change, a storage plan's existence will no longer prove that runtime maps are fused, every function is stored in the window root, or an optimized keyed restore/transplant is supported. Use explicit capability checks for those operations.

### Support anchor-only window roots [DONE]

An anchored DECIMAL SUM is an existing valid example with no fused component plan. The builder currently returns null for an empty group, and `LiveViewCheckpointWindowRoot` rejects payload widths less than or equal to the eight-byte anchor value.

Represent these cases with:

- A normal window root and window identity/key schema.
- An encoded manifest declaring zero components; the manifest byte array itself is not empty.
- An eight-byte scalar payload containing the anchor value.
- The existing function directory containing the functions' state.

Construct the window identity and key schema from the anchored window even when there is no eligible projection from which to infer them. Update construction, validation, freeze, restore, accounting, and incremental predecessor checks consistently. Merely relaxing the payload-length check is insufficient.

Keep manifest equality and key-layout compatibility checks. A single root type does not make two different component layouts interchangeable.

### Use one publication and restoration path [DONE]

Route both ordinary seals and repair publication through the window-root builder. Preserve the same output-key-domain semantics for anchor-only and component-bearing entries:

- Keys outside the repair domain retain the predecessor's entire entry.
- Replaced and removed keys are handled consistently across window and applicable function roots.
- Incremental and complete captures remain explicitly distinct.
- A partial replay cannot publish over an incompatible predecessor without rebuilding the missing state through an existing safe fallback.

Restore the window's key/anchor state and its component state into the active runtime representation, then restore any remaining function state in the required order. Ensure restoration never clears accumulator state that has just been reconstructed.

Keep specialized keyed-restore and live-transplant eligibility checks for residual functions and runtime capabilities. An anchor-only root does not imply that a key's entire state can be restored through one window-root lookup.

### Source-history preflight and blocked upgrades [WITHDRAWN - the blocked outcome is implemented, the preflight is not being built]

Automatic reset is permitted only after proving that the available source history can reproduce both the retained materialized output and the runtime state needed for continuation. The required range includes the view's historical replay range and any function warm-up required by its compiled semantics; availability of the current anchor segment alone is insufficient. The proof must cover a consistent applied-base transaction boundary and the live-view definition being recovered.

This is a required extension of the existing lifecycle. At the source baseline, `LiveViewCheckpointLifecycle.reconcile()` immediately removed a foreign-format directory, and `LiveViewRefreshJob.rebuildTimelineRecoveryFromAppliedBase()` can replace the whole materialized view range. Meanwhile, TTL, DROP/DETACH PARTITION, and TRUNCATE can remove source rows while retaining their live-view output and accumulated state. Reusing that unconditional reset would lose supported history.

The unconditional reset is gone for a declared foreign version: reconciliation now takes the blocked outcome instead, so the second row of the table below is implemented and the first is not. Nothing can yet reach the permitted outcome, because nothing can yet prove the evidence it needs.

The upgrade must have these two outcomes:

| Source-history evidence | Required outcome |
| --- | --- |
| Complete replay history is proven and remains available for recovery | Permit reset and rebuild through the sequence below. Preserve the view's existing results and correct accumulator continuation. |
| Required history is missing, or completeness cannot be established | Block automatic refresh and checkpoint publication for this view **before resetting anything**. Preserve the old checkpoint directory, materialized rows, view definition, and base table. The case then asserts the storage plan exists and names exactly the expected families with no residual, that the runtime binding follows the switch, reads the head window root back off disk, compares its manifest to the storage plan's byte for byte, and compares every key's whole payload - anchor value and each component's slots - to an image the test builds from the inserted values through the descriptor's own slot layout. Kahan and Welford are restated in the test at the formula level so the bytes agree exactly; the other families' fields are exact by construction. The restart flips the switch or leaves it, must record `timeline_restore` with zero rebuilds and resets, and must leave the very root phase one inspected as the head. Phase two adds the first contributing row for the empty key, a continuation that must not move the state (asserted on the root between rows for the extrema and counters), and an anchor crossing, then reads the root back again. Both phases end on the SQL oracle, a generic window over the day bucket, and on a zero refresh-fault count.

The cross-mode byte comparison is done against the independently computed image rather than by holding one mode's root against the other's: each mode must produce the same bytes as the values dictate, which is a stronger claim than that the two agree. Per row: `DOUBLE_SUM_COUNT` covers SUM, AVG and a derived COUNT; `DOUBLE_KAHAN_SUM_COUNT` seals with a compensation of -1.0 from `1e16 + 1.0` and asserts it is nonzero, so a restore that dropped it would answer the next row wrong; `DOUBLE_WELFORD` covers all four dispersion calls with a derived COUNT over zero, one and several contributions; the four extremum rows cover the NaN and `LONG_NULL` identities, values past 2^53 and separate LONG, DATE and TIMESTAMP identities; `NON_NULL_COUNT` keeps five standalone counters over DOUBLE, LONG, VARCHAR, SYMBOL and DECIMAL arguments; `ROW_COUNT` serves `count(*)`, `row_number()` and the guarded `count(account_id)` from one slot and includes a NULL partition key. Non-finite contributions are exercised through SQL NULL, which is NaN for a DOUBLE; no infinity is inserted.

Two contracts surfaced while writing it and are pinned rather than worked around. A component past the inline leaf budget is a runtime-only member of the group, not a residual: the plan's component count exceeds its durable count, `getResidualFunctions()` is empty, the two overflow projections are non-durable, and the root's function directory holds exactly two roots, in both modes and across every restart. And a restore re-establishes the incremental baseline: the first seal after a restart images only the key its row touched, in all four combinations, so the complete capture the matrix exercises is the view's first seal and the incremental ones are every later seal on both sides of the restart. The mixed residual DECIMAL/ROWS/RANGE cases stay where they were, in `LiveViewCheckpointMixedStateSealTest` and `LiveViewFusedShapeLifecycleTest`.

#### As implemented

Three things were built and one was measured.

**The capture ledger.** `LiveViewCheckpointCaptureLedger` is where the structural gate is read from, and it had to be added because nothing else in the system carries it. The freeze scratch the operation is bound to owns one - not the writer, because a suspended repair holds its own scratch across refresh turns and a writer-level ledger would be cleared out from under it by any cadence seal that worker ran in between. Binding a scratch clears it, `freezeWindowState`, `freezeFunction` and `freezeGroupedFunctions` charge into it, and the refresh worker copies it onto the view's `LiveViewInstance` once the publication is durable, where nine lifetime counters accumulate that a test or a benchmark reads by difference: window captures, incremental window captures, window keys visited/imaged/removed, function captures, incremental function captures, function keys visited/imaged. `LiveViewCheckpointTimelineStoreWriter.getCaptureLedger()` returns the cadence seal's, `RepairCapture.getCaptureLedger()` the repair's.

On the function side, `keysVisited` counts **walks**, not roots: one seal shares a single walk of a fused group's map across every runtime-only member that agrees on the incremental disposition, so a wide SELECT list adds roots and images without adding visits. `LiveViewWindow.getCheckpointLastFreezeVisitedKeyCount()` is the new reading the window half needs - imaged keys alone cannot say which map was walked, because a complete freeze of a fully touched domain images exactly what an incremental one would.

The counters are in-memory and reset on restart, and are deliberately not surfaced through `live_views()`, for the same reason the restore-route witness is not: they are a benchmark and test reading rather than an operator one.

**The driver.** `benchmarks/results/live-view-checkpoint-layout/` holds `run-matrix.sh` (one revision's half of the matrix, one JVM per run over a fresh database), `summarize-matrix.py` (per-run medians and p95s, then per-cell medians over runs, then the gate table), `baseline-harness.patch` (the benchmarks-only edit that makes the candidate harness compile on `6a2c656028`: the adopted plan instead of the storage plan, and -1 for the nine capture columns), `residency.py` (the `mincore` check behind the cold-restore cell) and a README with the exact commands.

The driver has four modes. `steady` and `repair` are described above. `churn` is the add/remove-keys, cross-anchor-boundary run: a `K`-account window (`--account-window=K`) over an anchor bucket of exactly `K` rows, a `K/1000`-minute anchor at 1000 rows per minute, which the harness slides by `K/2` accounts per bucket - half of a bucket's accounts recur and half are new, and the half left behind is evicted by the frontier sweep at the next boundary, with the compaction thresholds lowered (`--compact-threshold=1000 --compact-stale-percent=25`) so the sweep fires at all. Per cell the driver runs five independent JVMs, each seeding `K` rows into `K` round-robin accounts so the view holds exactly `K` live keys with nothing ageing out, then 110 commits of 1000 rows. Consecutive rows take consecutive accounts, so a commit touches exactly 1000 distinct existing keys - the changed-key domain the matrix fixes at 1000 independently of `K` - and `--checkpoint-rows=1000` makes one commit seal one boundary, so one batch row is one seal. ### Against these criteria, as implemented

- **Every newly published anchored checkpoint uses a window root; anchor-root production codecs/builders and conversion branches are gone.** Met, on both sides now. No seal, repair or compaction can publish an anchor root - `FrozenAnchor` and both of its publication arms are deleted - and nothing can read one either: the decoder, the builder, the reader's tagged union and the legacy component hoist are all gone, and `SLOT_FORMAT_VERSION` is advanced so a directory holding one is blocked rather than misread.
- **Runtime fusion no longer chooses the storage layout.** Met. All nine durable families, plus a SUM/AVG/COUNT shape one component past the inline budget, pass all four fusion/restart combinations in `LiveViewStateTransferFamilyMatrixTest`, with the root's manifest and every key's component bytes held to images computed from the inserted values and the restart held to the `timeline_restore` route.
- **Route-specific evidence for those combinations.** Met for the four routes a build without an authorized reset can take, `upgrade_blocked` included. The restart assertions in the fusion, keyed-repair and mixed-state suites no longer rest on a success flag both routes set, so a restore that stopped working now fails them. `upgrade_rebuild` waits on the preflight that would authorize a reset.
- **Recovery bundle, administrator operations, retention holds, blocked-upgrade behavior.** The blocked-upgrade behavior is implemented and tested, and it applies today to a timeline written by a build with another layout - a downgrade, or a node reading files from a newer one - rather than waiting on a bump. A blocked view reports `invalid`, keeps its rows queryable, and releases its base WAL floor rather than pinning it; the operator's exit is `SHOW CREATE LIVE VIEW`, `DROP LIVE VIEW`, re-CREATE. The recovery bundle, the administrator operations, the durable recovery record and the permitted (rebuilding) upgrade are **withdrawn**, not deferred: the `coverage` requirement they rest on is not satisfiable by any QuestDB deployment, and the operator's re-CREATE already performs the recovery they would have automated, with the same changed-history semantics stated out loud.
- **Performance matrix.** Met, with four requirements revised explicitly. The capture ledger, the harness shapes and controls, the result oracle, the cold-restart knob, the driver with its four modes, the aggregator and the baseline patch are implemented; the 10,000/100,000-key paired run, a 15-run re-measure of its failing cells, the 1,000,000-key scaling run, the closed-segment repair cell, the add/remove-keys churn run and the cold-cache restore are measured under the protocol, about 1,900 runs in all including the fourth round, one of which failed unreproducibly. The four gates that failed the flat limits are attributed - the fused entry's anchor bytes, a fixed one-to-four-millisecond cost on the two cold one-shot operations of the anchor-only shapes, and the unchanged-entry elision lookup paid for nothing when every anchor moves - and their requirements carry the measured impact rather than averaging it away. The fourth of them is the one the code now addresses: the freeze skips the lookup where nothing can be elided, which halves that cell's excess and brings its 10,000-key readings under the flat limit, and the requirement narrows to 0.3 ms per 1,000 keys imaged instead of being retired. The structural gate is a candidate-side claim because the baseline has no ledger to compare against, and under churn it was checked over every measured seal rather than by median.
